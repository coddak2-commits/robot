# 경유점 방식 롤백 기록 (2026-09-29 v1.1.203, 2026-09-30 v1.1.209)

실제 용접의 이동 방식을 아크 트래킹 여부에 따라 나눴다. 되돌릴 때 이 문서를 본다.

## 현재 동작 (v1.1.209~)

`robot-front/src/pages/UcellSelect/hooks/weldingCore/weldingExecution.ts`

```ts
const WAYPOINT_BLEND_MM = -1;
const useWaypoints = false;
...
await batchMoveL(batchPoints, { perPoint: useWaypoints, blendR: WAYPOINT_BLEND_MM });
```

수직·수평 구분 없이 전부 끝점까지 단일 MoveL, 블렌드 없음. 터치 보정은 끝점 것만 적용된다.

### v1.1.203~208 (블렌드가 남아 있던 구간)

| 조건 | 이동 방식 | 블렌드 | 터치 보정 |
|---|---|---|---|
| 아크 트래킹 ON + 수직 위빙 | 끝점까지 단일 MoveL | -1 | 끝점만 |
| 그 외 (트래킹 OFF, 수평 등) | 경유점 방식 | 50mm | 포인트마다 |

이 구간의 수평 설정이 2026-09-30 사고를 냈다. 아래 참고.

robot-core 로그로 구분한다.

- 단일 이동: `Skipping N waypoint(s), single MoveL to endpoint with endpoint offset`
- 경유점: `[per_point] queue preload: N points, blendR=...`

## 왜 바꿨나

- 수직 중간 포인트에서 끝 포인트로 넘어갈 때 방향이 꺾여 비드 모양이 바뀌었다 (2026-09-29 현장).
- 모재가 휘어 생기는 편차는 아크 트래킹이 잡는다는 전제다.
- v1.1.149~166이 쓰던 경로와 같다. 그때는 트래킹이 없어서 가운데가 직선으로 지나가 비드가 휘어 보였고, 그 이유로 v1.1.167에서 경유점 방식으로 바꿨다.

## 경유점 방식으로 되돌리기

`useWaypoints`를 항상 true로 두면 된다. 한 줄이다.

```ts
const useWaypoints = true;
```

블렌드는 그대로 두면 트래킹이 걸린 배치만 -1, 나머지는 50이 된다.
트래킹이 걸린 배치도 블렌드 50을 쓰고 싶으면 `WAYPOINT_BLEND_MM`도 `50`으로 고정한다.
단, 2026-09-29 v1.1.198 실측에서 **트래킹 ON + 블렌드 50 조합은 로봇이 시작점에 멈춘 채 MoveL
code=-4(XMLRPC 실행 실패)가 나고 컨트롤러 연결이 끊겼다.** 그 상태에서는 비상정지도 닿지 않고,
큐에 들어간 블렌드 이동은 컨트롤러가 계속 실행해 로봇이 혼자 움직였다. 이 조합은 다시 쓰지 말 것.

## 2026-09-30 사고 — 기어가기 + 블렌드 (v1.1.209에서 수정)

15:27 수평 파트에서 로봇이 끝점까지 정상 이동한 뒤 멈추지 않고 제자리에서 2분 넘게 용접했다.
비상정지가 닿지 않아 물리 정지로 끊었다.

로그의 결정적 지점.

```
15:27:43.369  MoveL vel=1 blendR=-1              <- v1.1.205 시작점 기어가기 3mm
15:27:43.914  [per_point] queue preload: 2 points, blendR=50.000000mm
15:27:43.926  [per_point] move 1/2 blendR=50.000000 ret=0
              (move 2/2 가 끝까지 안 찍힘)
15:29:46.375  EMERGENCY STOP -> code=-1 / stopMotion -> code=-2
```

`move 2/2`는 MoveL이 반환된 뒤에 찍히는 로그다. 반환이 없었다는 뜻이고, 그래서
아크 OFF도 못 나갔다. `[AnalogIn]` 값이 같은 시각부터 끝까지 고정된 것도
멈춘 MoveL이 모션 락을 쥐고 있었기 때문이다.

성립 조건은 두 개가 겹칠 때다.

| 조합 | 결과 |
|---|---|
| 기어가기 + 블렌드 -1 (수직) | 정상 |
| 기어가기 + 블렌드 50 (수평) | 물림 |
| 제자리 정지 + 블렌드 50 (v1.1.204 이하) | 정상 |

블렌드 이동만 완료를 기다리지 않고 바로 반환한다. 앞 이동이 아직 안 끝난 상태에서
다음 명령이 겹칠 수 있는 경로는 블렌드뿐이다. **기어가기(`PART_START_CREEP_MM`)를
쓰는 동안 블렌드를 되살리지 말 것.** 되살리려면 기어가기를 제자리 정지로 되돌려야 한다.

## 판단 기준

U셀이 휘지 않은 상태라면 단일 이동 쪽 비드가 더 낫다(2026-09-29 확인).
U셀이 휘어서 중간이 벌어지면 경유점 방식으로 되돌린다.

직선 이동이 실제로 얼마나 벗어나는지는 터치 결과로 계산할 수 있다.
아래·중간·위의 `find-dy` 값을 보고, 아래와 위를 직선으로 이은 중간값과 실측 중간값의 차이가 편차다.

| 런 | 아래 | 중간 | 위 | 직선 보간 중간 | 편차 |
|---|---|---|---|---|---|
| 2026-09-29 14:45 | -13.8 | -20.6 | -23.5 | -18.7 | 약 2.0mm |
| 2026-09-29 15:01 | 13.8 | 16.2 | 20.3 | 17.0 | 약 0.8mm |

2mm를 넘기 시작하면 경유점 방식을 검토한다.

### 수평 휨 실측 (2026-09-30 15:26)

터치의 `contact` 값이 면의 절대 좌표다. 보정값(`delta`)이 아니라 이 값으로 계산해야 한다.
티칭 경로 자체가 직선이 아니라서 보정값만 비교하면 편차가 과대평가된다.

| | 아래(y=-506) | 중간(y=-320) | 위(y=-80) | 직선 보간 | 편차 |
|---|---|---|---|---|---|
| x | -498.38 | -499.76 | -499.69 | -498.95 | 0.81mm |
| z | 3.63 | 2.21 | 2.02 | 2.92 | 0.72mm |

426mm 구간에서 약 1.1mm. 위빙 폭 안이라 단일 이동으로 두어도 무방하다고 판단했다.
수평은 평면 삼각파(코드 0)라 좌우 보정 조건에 안 맞아 아크 트래킹을 못 켠다.
즉 중간 편차를 잡아주는 것이 없으므로, 휨이 커지면 이 판단을 다시 봐야 한다.

## 관련 값

- `VERTICAL_WEAVE_CODES = [1, 5, 6, 7]` — 수직 계열 위빙 코드. 이 코드일 때만 트래킹을 건다 (v1.1.197).
- `welding_config.arc_tracking_enabled` — 0이면 `arcTrackingActive`가 false라 항상 경유점 방식으로 간다.
